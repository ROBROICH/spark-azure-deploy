# Alembic Utils Shared Library

Shared Alembic helpers for services that need safer autogenerated migrations and PostgreSQL history tables.

## Core Features

- **Idempotent migration operations:** Adds `IF NOT EXISTS` or `IF EXISTS` flags to common autogenerated Alembic operations.
- **Temporal table versioning:** Adds model and migration helpers for PostgreSQL history tables backed by a bundled trigger function.
- **Autogenerate hooks:** Keeps history tables out of normal schema diffs and emits the supporting DDL for versioned models.

## Architecture

### Overview

Alembic Utils is imported by a consuming service's Alembic environment. It does not run as a process. The service wires the helpers into `alembic/env.py`, then Alembic calls them during revision autogeneration or migration execution.

### Components

- **`safe_rewriter.py`:** Provides `safe_autogenerate_rewriter`, an Alembic `Rewriter` that makes generated DDL safer to rerun.
- **`temporal.py`:** Provides `VersionedMixin`, the history-table setup helpers, and the autogenerate callbacks for versioned tables.
- **`versioning/functions_v1.sql`:** Bundled PostgreSQL trigger function used by the temporal versioning helpers.

### Dependencies

| Module / Service | Purpose |
|------------------|---------|
| `alembic` | Migration framework that executes the generated operations. |
| SQLAlchemy | Supplied by consuming services for model metadata and table definitions. |
| PostgreSQL | Required when using temporal table versioning. |

## Getting Started

### Prerequisites

- Python `>=3.13, <3.14`
- `uv` package manager
- Alembic in the consuming service
- PostgreSQL when temporal table versioning is enabled

### Environment Variables

Alembic Utils does not read environment variables directly. Database connection settings are owned by the consuming service's Alembic configuration.

### Running the Module / Service

#### In Development

1. Add the workspace package to the consuming service:

   ```toml
   [tool.uv.sources]
   alembic-utils = { workspace = true }
   ```

2. Add `alembic-utils` to the consuming service dependencies.

3. Import the required helper in the service's `alembic/env.py` and pass it to `context.configure(...)`.

4. Generate and review revisions with the consuming service's normal Alembic command, for example:

   ```bash
   uv run alembic revision --autogenerate -m "add versioned table"
   ```

#### In Production

1. Package the consuming service with `alembic-utils` as a dependency.

2. Run the service's normal migration command during deployment or startup.

3. The helpers run inside Alembic; there is no separate Alembic Utils process to deploy.

## Usage

### Idempotent Autogenerate

Use the safe rewriter when configuring Alembic:

```python
from alembic_utils import safe_autogenerate_rewriter

context.configure(
    ...,
    process_revision_directives=safe_autogenerate_rewriter,
)
```

Autogenerated `AddColumnOp` and `CreateIndexOp` operations receive `if_not_exists=True`. `DropConstraintOp` and `DropIndexOp` operations receive `if_exists=True`.

### Temporal Table Versioning

Inherit persisted models from `VersionedMixin` and wire the versioning hooks into Alembic:

```python
from alembic_utils import VersionedMixin, build_versioning_hooks


class MyModel(Base, VersionedMixin):
    __tablename__ = "my_table"
    id: Mapped[int] = mapped_column(primary_key=True)


hooks = build_versioning_hooks(version="v1")

context.configure(
    ...,
    include_name=hooks["include_name"],
    process_revision_directives=hooks["process_revision_directives"],
)
```

During autogeneration, the hooks exclude managed `*_history` tables from normal diffs, create history tables for new versioned models, mirror compatible column changes to history tables, and tear down history infrastructure when versioned tables are removed.

### Manual Migration Helpers

Use the low-level helpers only when a hand-written data migration must manage versioning DDL explicitly:

```python
from alembic_utils.temporal import (
    install_versioning_function,
    setup_versioning_for_table,
    teardown_versioning_for_table,
    uninstall_versioning_function,
)


def upgrade():
    install_versioning_function(op, version="v1")
    setup_versioning_for_table(op, "my_table")


def downgrade():
    teardown_versioning_for_table(op, "my_table")
    uninstall_versioning_function(op)
```

Always pair manual setup with `VersionedMixin` on the model side. Do not define `sys_period` yourself.

## Public API

| Group | Exports | Purpose |
|-------|---------|---------|
| Safe autogenerate | `safe_autogenerate_rewriter` | Adds idempotency flags to common generated operations. |
| Versioned models | `VersionedMixin`, `SysPeriodType` | Adds the `sys_period` column used for temporal history. |
| Autogenerate hooks | `build_versioning_hooks` | Returns Alembic callbacks for versioned table diffs. |
| Manual DDL helpers | `install_versioning_function`, `uninstall_versioning_function`, `setup_versioning_for_table`, `teardown_versioning_for_table` | Creates or removes the trigger function, history tables, and versioning triggers. |

## Additional Notes

- Table names must fit within PostgreSQL's 63-character identifier limit after the `_history` suffix is appended.
- `VersionedMixin.sys_period` uses `TSTZRANGE` on PostgreSQL and falls back to `TEXT` on SQLite so model-level tests can run without PostgreSQL.
- Versioning SQL files are versioned by tag, such as `functions_v1.sql`; pass `version="v1"` when installing or building hooks.
